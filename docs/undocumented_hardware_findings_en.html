2. Undocumented Apple EFI ExitBootServices() Callback & Host Bridge Lock (HB80)

APPLE EFI00:00.0

Telemetry from M1A Probe proved that invoking AppleSetOs("Mac OS X 10.15") during UEFI Boot Services changes zero hardware registers immediately (pre-EBS PCI, GMUX, SMU7, and OpRegion states are 100% identical between Normal Boot Camp and SetOS boots). The actual firmware divergence occurs exclusively inside Apple EFI's registered EVT_SIGNAL_EXIT_BOOT_SERVICES callback.

PCI Register (00:00.0)Normal (Post-EBS)SetOS 10.15 (Post-EBS)Discovered Hardware Behavior
+0x54 DEVEN0x0000000F (D2EN=0)0x0000003F (D2EN=1)On normal Boot Camp boot, Apple EFI hides 00:02.0 (Intel iGPU) at ExitBootServices().
+0x80 HB800x000000010x00000001One-shot hardware lock bit for DEVEN! Proved in M1A-2 Mode [4]: once HB80=1, writing DEVEN.D2EN=1 post-EBS is silently ignored by silicon.
+0x58 PAVPC0x7FF000070x7FF00017Locks iGPU Protected Audio-Video Path memory (bit 4 set when iGPU remains enabled).
Architectural consequence: Intel HD 530 cannot be unhidden after a normal Boot Camp EBS due to the HB80=1 hardware lock. You must call AppleSetOs("Mac OS X 10.15") so Apple EFI skips its callback, and then replay the missing Polaris 11 initialization yourself immediately after ExitBootServices().

3. Exact 3-Register Polaris 11 VRAM Relocation (01:00.0 BAR5) & SMU7 Boot ROM

POLARIS 11KEY DISCOVERY

A 60-register X-Ray diff across Polaris 11's internal MC_VM, HDP, DCE0, VGA, SRBM, and VM_CTX blocks in m1a2_mode1_normal_xray proved that Apple EFI modifies exactly 3 registers on the AMD GPU during ExitBootServices() (the other 57 registers are 100% invariant):

Dword Index (BAR5=0x82600000)Register NamePre-EBSPost Apple EBSHardware Role in Polaris 11 MC/DCE
0x0809 (+0x2024)mmMC_VM_FB_LOCATION0x007F00000xF47FF400Relocates the 2 GB internal VRAM aperture to 64-bit MC range 0xF4_0000_0000 .. 0xF4_7FFF_FFFF.
0x0B01 (+0x2C04)mmHDP_NONSURFACE_BASE0x000000000xF4000000Points the Host Data Path (PCIe -> VRAM bridge base, in 256 B units) to 0xF4_0000_0000.
0x1A07 (+0x681C)mmGRPH_PRIMARY_SURFACE_ADDRESS_HIGH0x000000000x000000F4Upper 8 bits of active DCE0 framebuffer address. Requires a latch write to 0x1A04!
Why writing only 0x0809 corrupts the system: In M1A-2 v1 Mode [5], relocating only 0x0809 = 0xF47FF400 while leaving 0x0B01=0 and 0x1A07=0 produced green display snow/stripes (DCE scanning unmapped MC address 0x0) and crashed Windows boot with BAD_SYSTEM_CONFIG_INFO.

UEFI SMU7 State: In UEFI, Polaris 11's SMC runs strictly from its internal Boot ROM (ixSMC_PC_C advancing in 0x2718..0x2AC8, ram_running=0, ixRCU_UC_EVENTS=0x000F0084, ixSMU_FIRMWARE=0x00030006 = Protected Mode + Hard Key, ixSMU_EFUSE_49=0x00056B03 = AVFS=1). Without relocating MC/HDP to 0xF4_0000_0000, amdkmdag!polaris10_start_smu times out after ~207–269 ms with BugCheck 0x1B0 / P1=2 / P2=0xC0000001 and failure_bitmask=0x801 (Bit 0 + Bit 11). 

// Post-ExitBootServices 3-register relocation + DCE0 latch (uefi/m2_hybrid/mbp133_m2_hybrid.c)
UINT32 surf_lo = mmio_r32(bar5 + 0x1A04u * 4u);            // read low 32 bits (0x00300000)
mmio_w32(bar5 + 0x0809u * 4u, 0xF47FF400u);                // mmMC_VM_FB_LOCATION
mmio_w32(bar5 + 0x0B01u * 4u, 0xF4000000u);                // mmHDP_NONSURFACE_BASE
mmio_w32(bar5 + 0x1A07u * 4u, 0x000000F4u);                // mmGRPH_PRIMARY_SURFACE_ADDRESS_HIGH
mmio_w32(bar5 + 0x1A04u * 4u, surf_lo);                    // latch DCE0 surface update
io_delay_us(500);                                          // settle before Windows handoff

4. Pre-T2 Indexed I/O GMUX (Renesas R4F2113) & Hidden Apple AML Helpers in ssdt1.dsl

GMUX I/OACPI PEG0GFX0

MacBookPro13,3 exposes a Renesas microcontroller across I/O ports 0x0700–0x07FE using a two-phase indexed handshake. Unlike 2013–2015 Classic I/O GMUX Macs, you cannot read/write directly at 0x710 + reg:

I/O Port / IndexNameObserved Values & Behavior
0x07C2 (32-bit)GMUX_IO_VALUEData mailbox for 8-bit and 32-bit values (called BOX0..BOX3 in Apple AML).
0x07CC..0x07CEGMUX_IO_PROBEWrite 0xAA, 0x55, 0x00; reading 0x07CC..0x07CD returns signature 0x55AA.
0x07D0 / 0x07D4READ / WRITE+STATUSHandshake: wait for in8(0x7D4) & 1 == 0 → write index to 0x7D0/0x7D4 → wait for in8(0x7D4) & 1 == 1 → read/write 0x7C2.
Index 0x04VERSION0x04001D00 (Indexed I/O GMUX firmware version).
Index 0x10 / 0x28SWITCH_DISPLAY / DDC0x10: 0x02 = Intel IGD, 0x03 = AMD DIS. 0x28 (DDC/EDID): 0x01 = IGD, 0x02 = DIS.
Index 0x40SWITCH_EXTERNALExternal DP mux routing (0x01 at boot, 0x03 = DIS routes TB3 ports from AMD).
Index 0x50 + 0x16DISCRETE_POWER + IRQ_ST0x03 = AMD rail ON. Writing sequence 0x01 → 0x00 physically cuts AMD power (confirmed by Power IRQ bit 0x04 in port 0x16; idle draw drops to 9.34 W).
Index 0x70 / 0x74MAX_BRIGHTNESS / BRIGHTNESSMax 0x03FF (1023, 10-bit PWM). Backlight PWM remains wired through GMUX port 0x74 even when Intel drives the panel!
Hidden gem in Apple ACPI (ssdt1.dsl, TableId PEG0GFX0): Apple already ships native Indexed I/O GMUX AML methods inside Boot Camp ACPI: SGMX(Port, Len, Val) (generic indexed I/O helper on 0x7C2/0x7D0/0x7D4) and ABCM(Arg0) (scales 0–100 into (Arg0 * 0x03FF) / 100 and writes port 0x0774). Methods PUPD, PWRD, and GXWA also manage PEG0 L2/L0 link transitions (including SGMX(0x0750, 1, 3) to restore dGPU rail power).

5. Intel HD 530 (00:02.0): Native $VBT SKYLAKE, 4-Lane Strap DDI_A & BDB[43] Trap

INTEL iGPU101 BRIGHTNESS LEVELS
  • Complete native VBT inside OpRegion: Even though Boot Camp hides Intel HD 530 by default, Apple EFI still populates a full "$VBT SKYLAKE" (3,826 B, BDB ver=196, BDB[40].psr=0x00000000) inside Intel OpRegion Mailbox 4 (ASLS + 0x400). No external VBT blob is needed.
  • DDI_BUF_CTL_A (BAR0 + 0x64000): When Apple EFI boots from the AMD dGPU, it leaves bit 4 (DDI_A_4_LANES) cleared (0x00000081), even though internal panel APPA030 (2880×1800 @ 60 Hz) requires 4 DP lanes (DPCD rev=0x11, max_rate=0x0A, max_lanes=4). Intel-Only mode must force bit 4 (`0x81 → 0x91`). When booting with NVRAM gpu-power-prefs = iGPU, Apple EFI initializes it natively to 0x80000017.
  • Why brightness fails unless BDB[43] is zeroed: Apple's VBT sets BDB[43] (LFP Backlight Control) to 0x4A (type = 2, Intel PCH PWM). Because the physical panel backlight PWM is wired to the GMUX rather than the Skylake PCH, igdkmd64.sys writes to an unwired PCH register and the screen brightness never changes. Zeroing BDB[43] → 0x00 (NONE) + fixing VBT checksum vbt[26] instructs igdkmd64.sys to delegate brightness to ACPI \_SB.PCI0.IGPU.DD01._BCM → forwarded by our SSDT to Apple's native \_SB.PCI0.PEG0.GFX0.ABCM.
  • Only DD01 has _BCM: Unlike newer MacBook Pros, only \_SB.PCI0.IGPU.DD01 defines _BCM in DSDT (DD1F has no _BCM).

6. Apple NVRAM gpu-power-prefs & Windows PnP Surprise-Removal (Event ID 1011)

APPLE NVRAMBLACK SCREEN CAUSE

While developing Hybrid Mode 5, switching the GMUX to Intel just before chainloading Windows proved insufficient when Apple EFI had performed POST/GOP initialization on the AMD card:

NVRAM State (GUID FA4CE28D-B62F-4C99-9CC3-6815686E30F9 : gpu-power-prefs)Apple EFI POST BehaviorWindows 11 Outcome
Unset / deleted (default dGPU state)POST + EFI GOP run on AMD 01:00.0, GMUX on DIS (0x10=0x03), Intel DDI_A 4-lane bit cleared (0x81).Switching GMUX to IGD right before Hybrid Windows boot triggers PnP surprise-removal (Kernel-PnP Event ID 1011 on both GPUs at login) → black screen. Required for stock Boot Camp (AMD-only).
01 00 00 00 (iGPU)Apple EFI natively initializes Intel HD 530 as the POST/GOP primary GPU (GMUX 0x10=0x02, DDI_A=0x80000017, PP_STATUS=0x80000008).Windows boots cleanly on Intel HD 530 with zero surprise-removals. Caveat: booting stock Boot Camp without our loader while this NVRAM var is set causes Apple EFI to hide Intel at EBS while leaving GMUX on IGD → black screen (which is why EnsureGpuPrefsForMode() switches it automatically per mode).

7. Windows 11 dxgkrnl.sys Rejection of TypeIntegratedDisplay (0xC00000BB) & VFCT Layout

DXGKRNL.SYSATOMBIOS VFCTETW + KD PROOF

On the first Hybrid boot with gpu-power-prefs = iGPU and the 3-register BAR5 fix working, AMD still failed with Code 43 — yet produced zero WATCHDOG crash dumps! A live Microsoft-Windows-DxgKrnl ETW trace (run report) and kdX64.exe disassembly of C:\Windows\System32\drivers\dxgkrnl.sys revealed an undocumented WDDM kernel guard:

ETW Timeline during pnputil /restart-device:
1. dt = 1963.9 ms — amduw23g completes DxgkDdiStartDevice with STATUS_SUCCESS (SMU7 + 3-register relocation succeeded!).
2. dt = 1964.2 ms — DxgkDdiQueryChildRelations returns Child[0] with Type = 3 (TypeIntegratedDisplay), Caps = 0x80000000 (D3DKMDT_VOT_INTERNAL), AcpiUid = 0x0110.
3. Immediately, dxgkrnl!DpiFdoEnumChildDevices+0x3b7..0x3eb emits ID 549 (StartAdapter_DpiFdoEnumChildDevicesFailed) = STATUS_NOT_SUPPORTED (0xC00000BB).

Why? Windows 11 dxgkrnl.sys explicitly rejects any secondary (non-POST) GPU without an ACPI DisplayMux ([rbp+0A9Ch]==0 && [rbp+1901h]==0) if it reports a child output of type TypeIntegratedDisplay (3). The kernel bypass DpiHybridInternalPanelOverride is gated on g_OSTestSigningEnabled, making it unusable under standard Windows 11 with HVCI.

HVCI-compatible fix: amduw23g reads AMD's connector topology from ACPI table VFCT (VBIOS Flash Content Table, 60,548 B) and ACPI PEG0.GFX0._DOD. On an EfiACPIReclaimMemory copy of VFCT, we dynamically patch ATOM_OBJECT_HEADER_V3 (MasterDataTable index 22 @ vb+0x58CA):

8. Undocumented S3 Trap: Windows Enters PCIe D3 Before _PTS + Apple EFI Resets GMUX

ACPI S3CM_PROB_PHANTOMSOLVED

Testing lid-close Standby (S3) suspend/resume in Hybrid Mode uncovered two subtle hardware/ACPI interactions:

  1. Apple EFI resets GMUX to dGPU and powers rail 0x50 = 0x03 on every S3 resume: _WAK must explicitly restore SGMX(0x28, 1, 1), SGMX(0x10, 1, 2), SGMX(0x40, 1, 3), and ABCM(BRTL), otherwise the screen wakes up black.
  2. Windows puts PEG0/GFX0 into PCIe D3 BEFORE calling ACPI _PTS: Our Milestone 1B table SSDT_IGPU_MBP133.asl checked \_SB.PCI0.PEG0.GFX0.VID0 == 0xFFFF inside _PTS to detect Intel-Only mode. Because Windows already placed the PEG0 slot in D3 before _PTS, VID0 read 0xFFFF even in Hybrid Mode — causing _WAK to execute SGMX(0x0750, 1, 1); SGMX(0x0750, 1, 0) and physically cut AMD rail power on wake (`CM_PROB_PHANTOM`).
  3. AMD does NOT need post-EBS BAR5 re-patching across S3: With dedicated SSDT_HYBRID_MBP133.asl (which never touches port 0x0750), amduw23g cleanly resumes the dGPU from D3 to D0 and re-initializes VRAM on its own.

9. Split VT-d IOMMU (0xFED90000 vs. 0xFED91000) & Disproven Myths

VT-d IOMMUMYTHS BUSTED

ACPI DMAR on MacBookPro13,3 defines two separate VT-d DMA remapping engines: DRHD@0xFED90000 (dedicated solely to 00:02.0 Intel iGPU, disabled in UEFI GSTS=0x00000000) and DRHD@0xFED91000 (INCLUDE_PCI_ALL, active with translation enabled GSTS=0xC3000000, RTADDR=0x7AEFB000, covering AMD 01:00.0).

Disproven Hypothesis / MythObserved Experimental Proof
“igdkmd64.sys conflicts with the AMD driver”Disproven in M1A Reboot 2: Intel was disabled pre-boot (ProblemCode=22, igdkmd64.sys never loaded) and AMD still crashed with the exact same BugCheck 0x1B0 / 0xC0000001.
“AppleSetOs alters ACPI or VBIOS tables”All 24 ACPI tables (DSDT, SSDT1..12, VFCT, DMAR, MCFG) are 100% byte-for-byte identical between Normal Boot Camp and AppleSetOs.
“KMD_HybridGraphicsSupport registry keys enable Hybrid”Tested via pnputil + ETW: registry keys do not bypass the hard TypeIntegratedDisplay (0xC00000BB) rejection in dxgkrnl!DpiFdoEnumChildDevices.
“All AMD PCI/BAR registers must be cloned from Boot Camp”60-register X-Ray diff proved 57 internal registers are invariant; only 3 registers + the 0x1A04 latch differ.
